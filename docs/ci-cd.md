# CI/CDの導入メモ

## 状態と目的

今後対応するための検討メモです。CI/CDの設定はまだ実装していません。
実装と設定はユーザー自身が行い、Codexは相談・解説・レビューを担当します。

Vercelで本番公開する前に、GitHub Actionsでコードのチェックを自動実行することを目指します。
本番デプロイ元は `main` を想定しています。

## 導入するチェック

| チェック | 目的 | 実行方針 |
| --- | --- | --- |
| lint | コードの問題やルール違反を検出する | 違反があれば失敗させる |
| フォーマットチェック | 整形ルールに従っているか確認する | 自動修正せず、不一致があれば失敗させる |
| 単体テスト | 処理が期待どおり動作するか確認する | watchモードを使わず、1回実行して終了する |

TypeScriptを採用する場合は、型チェックの追加も検討します。
利用するツールと具体的なコマンドは、アプリの技術構成を決めてから選定します。

## 構成案A：PRでチェックし、VercelのGitHub連携で本番公開する

個人開発の手軽さを考慮した第一候補です。まだ採用は確定していません。

1. `main` から作業ブランチを作り、変更をpushする。
2. `main` 宛てのPRを作成する。
3. PRの作成・更新時に、GitHub Actionsで各チェックを実行する。
4. チェック成功と変更内容を確認してから `main` へマージする。
5. VercelのGitHub連携によって、本番へ自動デプロイする。

GitHubのブランチ保護で、PR経由の変更とチェック成功を必須にします。
直接pushや管理者によるルールの迂回も制限し、チェックを通さずに本番へ反映される経路を防ぎます。
一人での開発では、他者の承認を必須にする設定と、チェック成功を必須にする設定を区別してください。

この構成でチェックを待つのは、本番へ反映するためのマージです。
Vercelのプレビューデプロイは、Actionsのチェックと並行して実行されます。
Actionsを追加するだけでVercelがチェック成功を待つわけではありません。

## 構成案B：チェックからデプロイまでGitHub Actionsで実行する

`main` への直接pushを使う場合や、プレビューも含めてチェック成功後にのみデプロイしたい場合の選択肢です。

1. 対象ブランチへのpushやPRの更新をきっかけに、Actionsで各チェックを実行する。
2. 全チェックが成功した場合だけ、ビルド・デプロイの処理を実行する。
3. Vercel CLIを使い、`main` は本番、それ以外は必要に応じてプレビューへデプロイする。

チェックとデプロイの順序は、同一ジョブのステップ順やジョブ間の依存関係で保証します。
チェックを迂回するデプロイや二重デプロイを避けるため、対象のVercel Git自動デプロイは無効化します。
Vercelの認証トークンはGitHub ActionsのSecretsに保存し、リポジトリへコミットしません。

構成案Aに比べて、認証情報やデプロイ処理の管理が増えます。

## 無料プランと構成の選択

相談時点で確認した条件では、GitHub Freeのブランチ保護は公開リポジトリで利用できます。
非公開リポジトリでは、Actions自体の利用可否と、ブランチ保護によるチェックの必須化は別の条件です。
非公開のまま無料でデプロイ前チェックを強制する場合は、構成案Bを検討します。

Vercel Hobbyは個人・非商用向けで、利用量に上限があります。
GitHub Actionsにもリポジトリの公開範囲やランナーに応じた無料枠・料金条件があります。
導入時に最新のプラン条件を確認してください。

## 導入時に行うこと

- [ ] リポジトリの公開範囲と、構成案A・Bのどちらを使うかを決める。
- [ ] lint、フォーマッター、単体テストのツールと実行コマンドを用意する。
- [ ] TypeScriptを使う場合は型チェックの追加を検討する。
- [ ] ローカルで各チェックを実行できることを確認する。
- [ ] `.github/workflows/` にActionsのワークフローを用意する。
- [ ] 構成案Aではブランチ保護、構成案Bではデプロイの依存関係と認証情報を設定する。
- [ ] 意図的にチェックを失敗させ、本番公開に進まないことを確認する。
- [ ] 全チェック成功時に、想定した経路で本番公開できることを確認する。
